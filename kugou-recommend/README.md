# 推荐电台

给 [EchoMusic](https://github.com/hoowhoami/EchoMusic) 写的**多源音乐推荐**插件。
参考 [MakcRe/KuGouMusicApi](https://github.com/MakcRe/KuGouMusicApi) 的推荐类接口
（`everyday_*` / `fm_*` / `personal_fm` / `ai_recommend_*` / `top_song` / `user_history` / `youth_*`），
把它们编排成一个**能播、能续杯、能反馈**的推荐电台。

- 插件名：推荐电台
- 插件 id：`kugou-recommend`
- 版本：1.2.1
- 作者：YHuanheg
- 依赖：EchoMusic `>=2.3.2-beta.2`（需宿主已内置酷狗接口通道）
- 能力声明：`unrestrictedNetwork`（频道漫游需要直连网关）、`kugouVerification`（账号风控兜底）

> 插件不实现任何签名、设备指纹、RSA/AES —— 全部由宿主完成。它只做编排、归一化与展示。

## 八个推荐源

入口：侧边栏「插件」分组 → **推荐**（可在设置里关闭该入口）。

| 源 | 通道 | 登录 | 无限流 | 说明 |
|---|---|---|---|---|
| **频道漫游** | 概念版网关直连 | 否 | ✅ | `POST gateway.kugou.com/youth/v1/recommend/channel_wander`，可按标签定向，**默认源** |
| **每日推荐** | 本地路由 `/everyday/recommend` | 是 | — | 每天更新的一批个性化推荐 |
| **猜你喜欢** | 本地路由 `/personal/fm` | 否 | ✅ | 私人 FM 无限流 |
| **曲风推荐** | 本地路由 `/everyday/style/recommend` | 是 | — | 按曲风 tagids 出的日推 |
| **AI 推荐** | 本地路由 `/ai/recommend/song` | 是 | ✅ | 概念版 AI 推荐，支持翻页 |
| **新歌速递** | 本地路由 `/top/song` | 否 | ✅ | 最新上架歌曲榜 |
| **每日历史** | 本地路由 `/everyday/history` | 是 | — | 往期日推，可指定日期回看 |
| **听歌排行** | 本地路由 `/user/history` | 是 | — | 你自己的常听歌曲。⚠️ 该接口**只返回 `{hash,size,bitrate,privilege,level}`**，插件会用 `/privilege/lite` 按 hash 批量反查歌名/歌手/专辑/时长；同一首歌的多个 hash 变体会按 `albumAudioId` 塌成一条 |

「无限流」= 支持「再来一批」，且**开了去重后每批都真的不一样**；
非无限流的源同一时段返回同一批（这是上游特性，不是 bug），所以不显示「再来一批」。

### 每个推荐源各自保留自己的列表（多标签页式）

**切换推荐源不会丢掉你之前看的那批歌。** 每个源各自维护一份列表（含无限流的翻页位置）：

```
切到「每日推荐」→ 拉回 30 首 → 缓存到 everyday
切到「猜你喜欢」→ 拉回一批  → 缓存到 fm
切回「每日推荐」→ 直接恢复那 30 首，不发任何请求（提示「恢复上次的 30 首（3 分钟前）」）
```

- 源 chip 右侧会显示该源已缓存的条数（如 `每日推荐 30`），一眼看出哪些源已经拉过。
- 想换掉当前这批歌 → 点 **「换一批」**（这是唯一的刷新入口，语义明确）。
- **「不感兴趣」是全局的**：屏蔽一首歌会把它从**所有源**的缓存列表里摘掉，切回别的源也不会再冒出来。
- 缓存只存在**本次会话内存**里（8 个源 × 最多 300 首没必要写进宿主 KV），重启后从零开始；
  想立刻清空点统计卡里的 **「清空各源缓存」**。

> 「切源自动刷新」开关只作用于「切到的源**还没有**列表」这一种情况 ——
> 开（默认）就自动拉一批，关就给提示让你手动点「换一批」。已有列表的源永远直接恢复缓存，
> 否则每次切回来都重新请求，「保留列表」就失去意义了。

## 两条取数通道（为什么是两条）

EchoMusic 里其实有**两条**摸到酷狗数据的路，可用性差异很大，插件两条都用：

```
① 本地路由通道   ctx.electron.api.request({ url: '/everyday/recommend', params })
                 └─ 主进程内的 KuGouMusicApi 模块（resources/server/module/*.js）
                    路由换算规则： 模块文件名去掉 .js，再把 _ 换成 /
                    everyday_recommend.js → /everyday/recommend
                    ai_recommend_song.js  → /ai/recommend/song
                    签名 / 加密 / 设备指纹 / cookie 注入全部由宿主完成

② 网关直连通道   ctx.net.request({ url: 'https://gateway.kugou.com/youth/...' })
                 └─ 概念版（youth）网关，与官方插件 channel-wander 同源同款
                    特点：无需登录，是「没有账号也能用」的兜底
```

`channel_wander` 在本地模块目录里**没有**对应文件（宿主里只有标准版那 225 个模块），
所以它只能走通道 ②；其余源都走通道 ①（有本地模块，能借宿主的登录态与签名）。

## 播放、电台与反馈

| 能力 | 说明 |
|---|---|
| 单曲播放 | 点行首 ▶ 或双击行；会把该曲轮转到队首，后面接原顺序 |
| 播放全部 | 当前可见列表整批进队列 |
| 下一首播放 | 追加到「下一首播放」 |
| **推荐电台** | 一键开电台：拉一批 → 播放 → 队列快播完时**自动补充下一批**并追加，真正的无限听 |
| **每个源各自保留列表** | 像**多标签页**一样：每个推荐源各自记住自己上次那批歌，切回去**直接恢复、不重新请求**（源 chip 上会显示该源已缓存的条数）。想刷新就点「换一批」 |
| **切源自动刷新** | 只决定「切到的源**还没有**列表」时是否立即拉一批：开=自动拉（默认），关=给提示由你手动点「换一批」。页面工具条有快捷开关，设置面板也有 |
| 喜欢 | 收藏到本地「我喜欢」（可整批播放），落盘持久化 |
| 不感兴趣 | 立即从列表移除，写入本地屏蔽表，后续推荐**不再出现**（按 hash） |
| 跨批去重 | 同一会话内不重复推荐同一首；频道/FM 这类无限流靠它保证「换一批」真的换新 |
| 随机打散 | 拉回后打乱顺序 |
| 源健康检查 | 一键逐源打点，直接看到 **HTTP / error_code / 返回条数 / 耗时 / 失败原因** |
| 复制诊断 | 把登录态、当前源、参数、错误、健康检查结果打包成 JSON 进剪贴板 |

> **为什么内置「源健康检查」**：不同宿主机型、账号态、地区下各源的可用性差异很大
> （例如未登录时 `/user/history` 必然失败）。与其让用户对着「拉不到歌」猜，
> 不如给一个一键打点，把 HTTP 状态和 error_code 直接摊在界面上。

## 错误码对照

| error_code | 含义 | 插件行为 |
|---|---|---|
| `status: 1` + `error_code: 0` | 成功 | 正常展示 |
| 20018 / 51002 | 未登录 / token 失效 | 显示「登录状态无效，请在宿主里重新登录（该源需要登录）」 |
| 20010 | 上游拒绝该请求（参数或权限不符） | 实测 **AI 推荐**返回此码；两条 AI 路由都失败时，错误信息会同时点出两路的结果 |
| 20028 | 账号风控 | 自动调 `ctx.kugouVerification.request(eventId)` 唤起验证弹窗，通过后**原请求重试一次** |
| 21001 | 接口参数有误 | 展示可读文案，不重试 |
| 其他 | 未知 | 保留原始 HTTP / error_code 到健康检查表与「复制诊断」 |

宿主 `api:request` 的语义有两点反直觉、但必须记住（否则会写出永远失败的判断）：

1. **4xx/5xx 不抛异常**，正常 resolve；上游业务错误统一映射成 **HTTP 502 + 顶层 `error_code`**。
   所以不能按 HTTP 200 判断成功。
2. **`method` 被完全忽略** —— 方法由服务端模块自己决定（本地 `/youth/day/vip` 上游其实是 POST）。
   插件一律写 `GET`，不要让方法名误导你。

## 坑点（都实际踩过）

| 坑 | 现象 | 处理 |
|---|---|---|
| **hash 大小写不一致** | 真实 `channel_wander` 返回的 hash 是**大写**，其他接口给小写；同一首歌从两个源进来会被当成两首，去重失效 | 归一化时统一 `toLowerCase()`。宿主请求播放地址时自己也会 `toLowerCase`（`module/song_url.js`），所以不影响播放 |
| **封面带 `{size}` 占位符** | 直接当 `src` 用会 404 | 替换成 `400`，并把 `http://` 升级为 `https://` |
| **上游载荷层级五花八门** | `data[]` / `data.songs[]` / `data.song_list[]` / `data.info[]` 都有；channel_wander 还把歌包在 `item.song` 里 | 不做逐源解析，而是广度优先遍历对象图，挑「命中 hash 最多」的那个数组（`pickTrackArray`），再 `unwrapSong` 剥壳 |
| **时长单位** | 上游 `timelength` 是毫秒，宿主 `player.duration` 是秒 | 判 `>10000` 视为毫秒再 `/1000`；缺失时**不写** `duration` 字段，交给宿主从音频读 |
| **上游字段名 / 嵌套层不一致**（真机踩到） | `/user/history`（听歌排行）的歌名歌手既不在 `base` 上、也不叫 `songname`/`author_name`，真机上显示成「未知歌曲 - 未知歌手」 | 先按精确键名走 `firstOf`（点号路径），全落空后用**限深 BFS 按候选键名兜底**（`findFieldDeep`，深度 ≤3、节点 ≤120、只接受标量）；精确键名走第一遍、泛化键名（`name`/`title`）走第二遍，避免先撞上旁边的无关字段 |
| **响应本身就没有元数据**（真机踩到，与上一条是两回事） | 上一条修完仍显示「未知歌曲」→ 拿到原始键名才看清：`/user/history` 只返回 `{hash,size,bitrate,privilege,level}`，**根本没有歌名字段**，再怎么调 BFS 也变不出来 | 按 hash **二次反查**：`/privilege/lite`（KuGouMusicApi 里注释就是「获取歌曲信息」）接受逗号分隔的 hash，批量取回后**按 hash 配对**合并回原记录（原字段保留、大小写不敏感）。失败则降级展示并在健康检查里点名原因 |
| **同一响应里有多个「像歌曲」的数组** | 有的接口同时给「纯 hash 列表」和「带完整信息的列表」，只按 hash 命中数打分会在两者间随机选，可能挑到光秃秃那个 | 挑数组打分改为 `带名称信息条目数×5000 + 命中hash条目数×1000 + 数组长度` —— 名称信息是更强的信号 |
| **超长了就得切开** | `/privilege/lite` 的 hash 参数会无限长 | 批量上限 50 个/次（`ENRICH_BATCH`），后续需要再分片 |
| ⚠️ **写「从 reactive 容器 new 出来的原始对象」会绕过 Proxy**（真机踩到，最难查的一个） | 表现：**点「换一批」新歌不显示，切到别的源再切回来才出现**。原因：`bucketOf` 首次创建 bucket 时把刚 `new` 的原始对象直接 return 了，后续 `bucket.tracks = ...` 写的是原始对象 → 绕过 reactive 的 set 陷阱 → 依赖它的 `computed` 不失效、**缓存住旧值**，界面就一直渲染旧列表，直到别的依赖（如 `sourceId`）变化才重算 | 必须**先写进响应式容器、再从容器读回来**：`state.lists[id] = {...}; return state.lists[id]` —— 从 `reactive` 对象里读出来的才是 Proxy。同理，任何 `const b = state.x; ...; b.y = v` 之前都要确认 `b` 是代理 |
| **反查接口只给「歌手 - 歌名」复合串** | `/privilege/lite` 的 `name` 是 `"涂一乐 - 花落叹"`，直接用会显示成「涂一乐 - 花落叹 - 涂一乐」 | `cleanupTitle(title, artist)`：只有当分隔符左侧**与歌手完全一致**且右侧还有内容时才剥前缀，避免误伤本身带连字符的正常歌名 |
| **同一首歌的多个 hash 变体会显示成好几条「一样的歌」**（真机踩到） | 听歌排行会返回同一首歌的多个 hash（不同音质/版本），只按 hash 去重就会列出一堆同名行 | 区分两个身份：`dedupeKey = hash`（文件级）与 **`songKey = albumAudioId \|\| hash`（歌曲级）**；批量去重用 `songKey`，把同一首歌的多份文件塌成一条，而 `albumAudioId` 不同的歌不会被误合并 |
| **归一化失败时无从下手** | 只看到「未知歌曲」，不知道上游把字段放在哪一层、叫什么 | 健康检查把**上游第一个条目的原始键名**（剥壳前 + 剥壳后）与截断 JSON 一起带出来，「复制诊断」即可精确校准；列表里未识别的条数会打 `⚠ N 首未识别` |
| **`/everyday/history` 的 `mode`** | 模块注释只写了「mode list ,song」；一直用 `mode=list` 会让「按日期回看」失效 | 不填日期走 `mode=list`；填了日期走 `mode=song` + `date`；若列表里没有歌，先取出记录里的日期字段再二次请求 |
| **AI 推荐返回 20010** | 概念版 `/ai/recommend/song` 在本机账号下被上游拒绝 | 做主备两条路：`/ai/recommend/song` 失败后回退 songlistairec 版 `/ai/recommend`；两条都失败时把两路的结果一起报出来。真机复测：**回退路可用，已能返回 12 首** |
| **主 hash 取错来源** | `hash_320` / `hash_flac` 是「另一份音质的文件」，不是歌曲的规范标识；若把它们当主 hash，宿主会拿它当身份去解析地址 —— 能播但身份/封面/去重都会错位 | 主 hash 只认 `hash` / `hash_128`（`audio_info` → 顶层 → BFS 兜底），**只有整条链都找不到规范 hash 时**才退回 320/flac；320/flac 的 hash 一律归入 `relateGoods` |
| **网络层临时失败被当成「源不可用」** | 真机实测 `/user/history` 偶发 `HTTP 502 + net::ERR_CONNECTION_RESET`（`error_code` 为 0） | 判别式：**酷狗业务错误一定带非零 `error_code`**，所以「502 且 `error_code=0`」= 上游连接问题 → 自动重试一次；而 20010/21001 这类业务拒绝绝不重试（重试也无效，还徒增风控风险）。健康检查里重试过的源会标 `（重试后）` |
| **`error_code=0` 被写成「成功」** | `error_code` 为 0 表示「没有业务错误码」，但错误码表里 `0 → 成功`，直接查表会把失败文案显示成「成功」 | 先判断 `code` 是否非零，非零才走错误码表；否则用上游的 `error` / `msg` 文本（这样才看得到真实的 `net::ERR_...`） |
| **单列表 → 按源分桶是个「全量替换」式重构** | 把 `state.tracks` 换成 `state.lists[源id]` 时，所有读写点都得跟着改，漏一处就会串源或丢数据 | 读写点一共 8 处：`loadBatch`（replace/append + page）、`loadMore`、`maybeRefill`、`block`、`playTrack`、`visibleTracks`、`onMounted` 守卫、诊断快照。做法是**只通过 `listOf(id)` / `bucketOf(id)` 两个入口访问**，并额外让 `block()` 遍历所有桶（屏蔽是全局语义）。重构后测试从 227 条加到 239 条，全部通过 |
| **插件页不能滚动** | 宿主把插件页包在 `.plugin-page-host`（`h-full min-h-0 overflow-hidden`），只裁剪不滚动 | 页面根元素自己做滚动容器，且**不能用 flex-column**（子项 `flex-shrink:1` 会把内容压扁）；底部留 140px 给播放条 |
| **「换一批」按钮对有限流没意义** | 每日推荐同一时段返回同一批 | 对非无限流源禁用该按钮并给出提示；无限流源才走过去重 |
| **无限流被去重吃空后卡住** | 本页的歌都出现过 → 清空后页码没推进 → 一直拉同一页 | 取数成功后**即使本批为空也推进页码**，并自动多翻 1–2 页 |
| **`vnode` 会捕获渲染时的状态** | 切换状态后复用旧 `vnode` 连点两次，第二次仍发送旧值 | 改状态后必须重新渲染再取 `vnode`（测试里已按此写） |
| **测试夹具自己的 bug 最坑** | 踩了两次：① 自写的 LCG 生成 hash 低位周期只有 16，5 首歌里就撞了 2 个重复 hash；② `fmBody` 的 `hash_320` 用了 `hashOf(s+300)`，正好撞上 `topSongBody(1200)` 的 seed，被插件**正确地**去重滤掉，看起来却像插件坏了 | 夹具一律用 `md5` 生成确定性 hash，**并且各夹具的 seed 区间必须互不重叠**（现在 fm 用 `s+5000`，并在注释里写明原因） |

## 安全边界

- 只读写自己命名空间下的 `ctx.storage`（`plugin:kugou-recommend:*`）；
- 网络请求只有两个去向：**宿主内置的酷狗接口通道**、**酷狗概念版网关**；
- 不采集、不上传任何数据；不写宿主的任何设置项。
