# 歌曲下载（`song-downloader`）

> 当前版本 **1.4.0** · 需要 EchoMusic **≥ 2.3.2-beta.2**（本地接口通道）

把「当前播放」或「播放队列」里的歌下载到本地：下载前弹确认框选音质 / 保存位置 / 文件名，
播放栏与标题栏都有**一键下载**按钮，分片下载带**真实进度与速度**，支持批量任务、失败重试与直链复制。

装完即用，不用配任何东西 —— 侧边栏「插件 → 下载」是主入口，另外两处快捷入口默认也开着：
**播放栏右侧**的下载图标、以及**标题栏**的下载按钮（都能在设置里关掉）。

```
下载歌曲                                        ✕
┌──────────────────────────────────────────────────────┐
│ ♪  花落叹 / 涂一乐 · 某专辑                          │
│    可用音质： 128K  320K  FLAC                        │
│                                                      │
│ 音质    ( 自动（最优可用） ) ( FLAC ) ( 320K ) ( 128K )│
│         实际会使用：FLAC                              │
│                                                      │
│ 保存位置 ( 系统下载目录 ) ( 选择位置… )               │
│         落到系统下载目录（Windows 通常是               │
│         %USERPROFILE%\Downloads）；想指定位置点        │
│         「选择位置…」                                  │
│                                                      │
│ 文件名  [ {artist} - {name}                        ]  │
│         将保存为：涂一乐 - 花落叹.flac                │
│                                                      │
│ ( ✓ 分片下载（显示进度与速度） ) ( ✓ 完成后弹提示 )    │
├──────────────────────────────────────────────────────┤
│ ( ✓ 记住这些选项 )              [ 取消 ] [ 开始下载 ] │
└──────────────────────────────────────────────────────┘
```

## 一、功能

| 功能 | 说明 |
| --- | --- |
| **任务中心** | 每个下载任务在标题栏「任务中心」占一行，带**进度条与百分比**（`下载中 62% · 12.4 MB / 32.1 MB · 1.8 MB/s`），可直接在那里**停止 / 重试 / 复制直链**；完成后 8 秒自动收起，失败会留着等你处理 |
| **下载确认框** | 每次下载前弹窗确认：音质 / 保存位置 / 文件名模板 / 分片与提示开关，可勾「记住这些选项」写回设置，也可在设置里整体关掉 |
| **播放栏 + 歌词页按钮** | 主播放栏右侧（收藏 / 播放队列那排）和**歌词页底栏右侧**各插一个下载图标；没歌在播时自动置灰；设置里可关 |
| **标题栏按钮 / 命令** | 标题栏一个「下载」按钮，外加 3 条命令（下载当前 / 另存为 / 停止全部） |
| **下载当前歌曲** | 一键下载正在播放的歌（优先复用宿主已解析的地址，见 2.5） |
| **批量下载队列** | 勾选播放队列里的任意多首一次下载（支持全选 / 清空选择），共用一个确认框 |
| **自动音质选择** | 「自动」= 该歌可用的最高音质；不可用时**逐级降级**（flac → 320 → 128）并在任务行标明实际音质 |
| **可用音质标签** | 每首歌旁显示它真正可用的音质（来自版权信息），不是拍脑袋的固定值 |
| **真实进度与速度** | 默认按 Range 分片（1 MiB/片）下载，因此能算出真实百分比、瞬时速度与剩余时间 |
| **失败重试** | 网络异常 / 5xx 自动重试（次数可配）；4xx 不重试（重试没意义） |
| **可中断** | 「停止」在分片之间生效；「全部停止」一次停掉整队 |
| **下载历史** | 最近 200 条落盘持久化，含音质、体积、耗时、是否分片；可一键复制当次直链 |
| **直链复制** | 解析出带签名的真实播放地址并复制，交给 IDM / aria2 等外部下载器 |
| **另存为…** | 内核支持 File System Access API 时可选任意位置保存（仅单曲） |
| **诊断导出** | 一键复制设置、任务、历史与最近一次解析结果，排障时直接贴 |
| **可疑试听提示** | 实际字节远小于「码率 × 时长」时给出「可能只是试听片段」的告警 |

## 二、三条技术线（决定了插件能做到什么）

### 2.1 取播放地址：走宿主内置的酷狗本地路由

```js
ctx.electron.api.request({ method: 'GET', url: '/song/url', params: { hash, quality, album_id, album_audio_id } })
// → { status, body, cookie, headers }
```

主进程内的 KuGouMusicApi 模块（`resources/server/module/song_url.js`）负责签名、加密、设备指纹与 cookie，
插件一行都不用写。三条实测出来的宿主语义：

1. **`method` 被完全忽略** —— 模块自己决定上游方法（`/song/url` 上游其实是 GET，但别处有 GET 走 POST 的）；
2. **上游业务错误 = HTTP 502 + 顶层 `error_code`，不抛异常** —— 所以判断成功不能只看 `status`；
3. **`error_code` 为 0 表示「没有业务错误码」**，绝不能拿 0 去查错误码表（表里 0 往往是「成功」，
   会把失败显示成成功）。

### 2.2 音质与 hash：完全对齐宿主 PlayerResolver

- 可用音质来自 `track.relateGoods`（宿主会把 `/privilege/lite` 的结果写回轨道上），
  匹配表：`320/hq/level4`、`flac/sq/level5`、`high/hires/level6`、`viper_tape/level101`；
- **每种音质对应不同的 hash**，取地址必须用该音质自己的 hash，否则拿到的是别的文件；
- **只有 128 例外**：它必须用轨道主 hash —— `qualityMatch(entry,'128')` 恒为 true，
  若直接 `find` 会命中数组第一条（可能是 flac 那条），拿到错误的音频（测试里专门放了乱序夹具防回退）。

### 2.3 落盘：宿主没给插件「写任意路径」的能力

这是本插件最容易被误解的一点 —— 不是没做，而是三条路都被宿主堵死了（asar 逐字节核验）：

| 通道 | 实际限制 |
| --- | --- |
| `ctx.fs.writeFile` | 路径被硬限制在**插件目录内**（`ip()` 里 resolve + relative 校验），且单次写入 **≤ 8 MB** |
| `ctx.process.launch` | 只允许启动**插件目录内的 `.exe` / `.com`**，且每次弹窗要用户授权，还会校验 exe 哈希 |
| 主进程 | 没有注册 `will-download` / `setDownloadPath`，也没有向插件暴露任何「保存对话框」 |

所以插件的做法是：

```
主通道   Blob + <a download>  →  交给 Chromium 自身下载行为  →  系统默认下载目录
可选通道 window.showSaveFilePicker()（File System Access API）→ 用户自选任意位置（仅单曲）
兜底     「复制直链」→ 交给外部下载器（同时规避 8 MB / 目录限制）
```

「另存为」必须**在用户点击手势内**调用 picker，所以流程是「先弹对话框选位置，再入队下载」，
而不是下载完再问 —— 后者会因瞬时激活（transient activation）过期而必然失败。

### 2.4 风控（安全验证）：不接就会「每一首都失败」

宿主主进程的 request 层会把上游的 `ssa-code` 同时写进 `headers['ssa-code']` 与 `body.ssaCode`
（失败时 body 里还带 `edt` / `sid` 行为指纹），但**插件这一侧没有任何自动兜底**：
不自己唤起验证弹窗，用户看到的就是每一首都在「本次请求需要验证」。

```js
const eventId = body?.ssaCode || res?.headers?.['ssa-code'] || body?.data?.event_id
if (eventId && (errorCode === 20028 || Number(body?.status ?? 1) === 0)) {
  const verified = await ctx.kugouVerification.request(eventId)   // 需 manifest 声明 kugouVerification
  if (verified?.ok) res = await ctx.electron.api.request(config)  // 通过后原样重试一次
}
```

三个实现细节（都做了测试）：

- **判定必须带「请求确实失败」**：某些接口成功响应里也会带 ssaCode（只是提示可做二次验证），
  那种情况不该弹窗打扰用户；
- **同一轮只弹一次**：取地址会逐档试 flac→320→128，若每档都弹一次，用户会以为插件坏了。
  用 `verifyState = { done, ok, error }` 在整轮里记住结果，第一档没过就把它报上去，
  点「重试」才会再验（新的一轮）；
- **能力缺失要明说**：老宿主 / 没声明能力时，直接告诉用户「宿主未提供安全验证通道」，不要静默失败。

### 2.5 正在播放的这一首：直接复用宿主已解析的地址（最稳的一条路）

宿主自己的播放器取地址同样走 `/song/url`：

```js
function Pf(hash, quality, ppageId) { return Q.get('/song/url', { params: { hash, quality, ... } }) }
```

差别在于那层 `Q` **自带风控兜底**：拿到响应后 `Wd()` 取 `ssaCode` → 唤起验证 → 带
`retriedAfterKugouVerification` 重试整个请求。而**插件侧的 IPC 通道没有任何兜底** ——
这就是为什么「宿主能播、插件下载却报需要验证」。

既然宿主已经把这首的可播地址解出来了，就没有理由再请求一次。player store 里就是：

| 字段 | 含义 |
| --- | --- |
| `ctx.stores.player.currentTrackId` | 当前曲目 id（用来确认「这首就是正在播的」） |
| `ctx.stores.player.currentAudioUrl` | **播放器正在用的那条地址** |
| `ctx.stores.player.currentAudioCandidateUrls` | 备用地址（一起当地址候选） |
| `ctx.stores.player.currentResolvedAudioQuality` | 宿主解析出来的音质（用来显示 + 判断够不够） |

于是下载顺序变成：

```
① 当前正在播 + 「优先借宿主通道」开关开 + 宿主音质够用 → 直接用 currentAudioUrl（0 次上游请求，0 风控）
② 请求「自动」时 → 请宿主解析器解析这首的地址（它自带风控兜底：会弹宿主自己的验证窗并自动重试）
③ 否则自己请求 /song/url（带插件侧的验证兜底；显式选音质时走这条，才不会被宿主的音质糊弄）
④ 自己请求被风控拦下（且用户没主动取消验证）→ 再借宿主解析器救一把
⑤ 都失败时，用曲目对象上残留的宿主 audioUrl 兜底（可能还没过期）
⑥ 用了 ①/②/④/⑤ 的地址却下载失败（地址过期等）→ 回退到 ③ 重新解析一次再试
```

**②/④ 就是「向宿主模拟请求播放、但不真的播放」**：宿主把纯解析器放在 player store 上 ——
`ctx.stores.player.resolveAudioUrl(track, { forceReload })`。它只解析（内部会顺带补 `relateGoods`），
**不写 `currentAudioUrl`、不切歌、不动队列**，但走的是宿主自己的 API 层 `Q.get('/song/url')`，
所以宿主的验证兜底全部生效。插件侧拿不到的那层兜底，这里一次性补上。

曲目对象上的 `audioUrl`（宿主解析后写回的）必须**原样保留到任务快照里** ——
1.1.1 的归一化把它丢了，导致 ⑤ 这条兜底永远走不到（被测试抓到）。

音质取舍：请求「自动」时跟着宿主的播放音质走；显式要更高音质（比如宿主在放 320K 而你要 FLAC）时
不偷懒，老老实实去请求上游 —— 毕竟你要的就是那个更高音质。

## 三、下载与进度是怎么做的

宿主 `ctx.net.request` **没有字节回调**，所以「真实进度」只能自己造：默认按 Range 分片。

```
① 探测   Range: bytes=0-0        → 206 + content-range: bytes 0-0/<总长>   ⇒ 拿到总长，顺便知道服务端支持 Range
② 分片   Range: bytes=x-y        → 206 + 该段字节                          ⇒ 累积 + 每片回调一次进度/速度
③ 兜底   服务端忽略 Range（200）  → 直接把整包当结果（不再重复请求）
④ 兜底   分片中途开始忽略 Range   → 若返回体 ≥ 总长则当整包，否则报错
⑤ 兜底   探测失败 / 关闭分片开关  → 一次性下载（只有总进度，没有中间进度）
```

两个容易踩的坑：

- **`maxResponseBytes` 必须显式传 0**。宿主默认 **32 MiB**，一张 FLAC 可能更大，会被截断成半首歌；
  传 0 等于「不限制」（主进程里映射成 `maxContentLength: -1`）。
- **取消不传 AbortSignal**：它要跨 IPC 序列化，风险大于收益。改为在分片之间检查取消标志，
  代价是「停止」的生效粒度 = 当前分片下载完（≤ 1 MB 的等待）。

## 四、设置项

| 设置 | 默认 | 说明 |
| --- | --- | --- |
| 下载前弹确认框 | **开** | 关掉后所有下载入口都用下面的默认设置直接开始，不再弹窗 |
| **复用宿主已解析的播放地址** | **开** | 正在播放的那首歌直接用播放器已解析好的地址（音质跟随播放音质）：不发请求，也就不会触发风控。关掉则一律自己请求上游 |
| **同步到标题栏「任务中心」** | **开** | 每个下载任务在任务中心占一行（进度条 + 百分比 + 停止/重试/复制直链）；完成后 8 秒自动收起，失败留着 |
| 默认音质 | 自动（最优可用） | 可固定为 128K / 320K / FLAC / Hi-Res / 母带；不可用时仍会降级 |

| 失败重试次数 | 1 | 每个分片 / 整包的重试次数，0 = 不重试 |
| 同时下载数 | 1 | 1–2，默认 1（对上游 CDN 更友好） |

| 顶部工具栏入口 | 关 | 标题栏的「下载」按钮 |
| **播放栏下载按钮** | **开** | 播放栏右侧那一排里的下载图标 |
| 完成时弹提示 | 开 | 关掉后只在任务列表里看结果 |
| 调试日志 | 关 | 控制台输出解析与下载细节 |

## 五、四个交互是怎么挂上去的（都踩过坑）

### 5.1 设置页为什么不能自带滚动

宿主的插件页与插件设置**不是同一套容器**：

| 容器 | 宿主类名 / 结构 | 谁负责滚动 |
| --- | --- | --- |
| 插件页 | `.plugin-page-host`（`h-full min-h-0 overflow-hidden`，有**确定高度**） | **插件自己**：根节点必须 `height:100%` + `overflow-y:auto` |
| 插件设置 | 弹窗 `.plugin-settings-dialog` → `el-scrollbar` 包 `.dialog-scroll-area`（`flex-1 min-h-0`） | **宿主** |

所以在设置根节点上写 `height:100%` + `overflow-y:auto` 会变成「自己高度 = 内容高度 → 自己滚不动」，
而宿主的滚动容器又量到「没有溢出」→ **整页完全不滚**（1.0.0 的真实 bug）。
现在 `.sd-settings` 只做普通流式布局，滚动全交给宿主 —— 测试里有一条 CSS 契约断言专门锁死这一点。

### 5.2 确认框挂到 `document.body`

插件页/设置弹窗都有 `overflow:hidden` 的祖先，就地渲染会被裁掉（尤其页面切换动效会加 transform，
连 `position:fixed` 都会跟着被裁）。所以确认框走宿主的浮层通道：

```js
const dispose = ctx.ui.teleport(DownloadDialog, { id: 'song-downloader-dialog', className: 'sd-teleport' })
```

组件内部用 `dlg.open` 控制渲染与否，Esc / 遮罩点击 / Ctrl+Enter 由 activate 里注册的全局 keydown 处理
（放在 activate 而不是组件 `onMounted`：teleport 出去的是独立 app 实例，用全局监听更简单、卸载时也一定摘得掉）。

### 5.3 播放栏按钮走 `ctx.ui.mount` + MutationObserver 兜底

播放栏没有「插件按钮」这种一等公民 API，但宿主给了 DOM 挂载通道：

```js
ctx.ui.mount(hostEl, PlayerBarButton)   // 默认 append 成子节点；{position:'after'} 则是插入兄弟节点
```

**要贴三个容器**（同一时间只可能看到一处），按组各挂一个、取第一个命中的选择器：

| 组 | 候选容器 | 说明 |
| --- | --- | --- |
| 主播放栏 | `.player-actions` → `.player-bar` | 分享 / 收藏 / 播放队列那一排 |
| **歌词页底栏** | `.lyric-bar .bar-right` → `.lyric-bar .bar-song-actions` → `.lyric-bar` | 深色底：宿主样式里 `.lyric-bar .bar-right button{color:#ffffff80!important}` 会自动把颜色刷成白色，所以挂进 `.bar-right` 配色天然融入 |
| 迷你播放器 | `.mini-card .mini-actions` → `.mini-card` | 需要 `manifest.runtime.miniPlayer`，当前未开，留着以后用 |

两个必须处理的现实：

1. **宿主页面是后出现的** → 用 `ctx.dom.observe('.player-actions' / '.lyric-bar' / '.player-bar', ...)` 等它出现，
   而不是 activate 时硬查；
2. **宿主原地重渲会把我们塞进去的节点抹掉**，而 `dom.observe` 对「同一个元素」不会二次回调
   → 额外用防抖的 `MutationObserver` + 1.5s 轮询把按钮补回来。每次挂之前先做两件事：
   容器里已经有 `.sd-bar-btn` 就跳过（同一排不挂两个），换了容器/被抹掉了才 `dispose()` 旧的再挂；
   容器消失（比如退出歌词页）就把那一组收掉。

按钮本身用**内联 SVG**而不是宿主的 `icons.*`：宿主只导出 `iconCloudDownload` 这类零散图标，
名不副实（换版本还可能改名），内联 SVG 是唯一稳定的做法。

### 5.4 「选择位置」必须先解析、再弹保存对话框（0 KB 空文件的根因）

`window.showSaveFilePicker()` **一确认就先把 0 字节文件建出来**，真正写入在之后。
所以 1.1.0 的「先弹对话框再下载」在失败时会留下一堆 0 KB 同名文件（用户真实反馈）。
1.1.1 把顺序倒过来：

```
点「开始下载」→ 解析播放地址（可能弹安全验证）→ 弹保存对话框 → 下载字节 → 写入
                └─ 失败就在这里返回：磁盘上什么都没建
```

配套三点：

1. 弹窗里点「选择位置…」**只标记状态**，不立刻弹对话框；界面会写明「先解析、再弹对话框」；
2. 解析耗时算在用户手势的 5 秒窗口里（picker 必须在窗口内调用）。超时会 `NotAllowedError`
   → 优雅降级到系统下载目录，不报错卡住；
3. 仍然失败时兜底清理：`handle.remove()` 在 Chromium 里实现不齐，`try/catch` 之后
   清得掉就在错误里写「已清理失败留下的空文件」，清不掉就点名文件让用户手动删。

另外用「代际令牌」处理用户中途关弹窗：每次开/关 `dlgGen += 1`，解析或对话框 await 之后比对，
不一致就作废（顺带把刚建出来的空文件删掉），避免「界面已关、文件却下下来了」。

### 5.5 下载任务同步到标题栏「任务中心」

宿主有**正式接口**，不需要 DOM 注入（asar 核验；宿主自己的「任务中心」标题栏项也是同一套）：

```js
const handle = ctx.tasks.register({
  id: 'song-downloader:<taskId>', // ⚠️ 不能用 echo: 前缀（宿主保留给内置任务，会抛错）
  name: '花落叹 · 涂一乐',
  status: 'pending',              // pending(待操作) running(进行中) completed(已完成) error(失败) aborted(已中止)
  progress: { percent: 42, label: '下载中 62% · 12.4 MB / 32.1 MB · 1.8 MB/s' },
  actions: [{ id: 'cancel', label: '停止', variant: 'ghost', onClick: () => cancelTask(task) }],
  retention: {                    // ⚠️ **必填**
    completed: { mode: 'auto', delayMs: 8000 }, // 完成后 8 秒自动收起（看得见结果，又不堆屏）
    error: { mode: 'manual' },                  // 失败常驻，等用户处理
    aborted: { mode: 'auto', delayMs: 3000 }
  }
})
// handle: { active, signal, cancel(), start(patch), update(patch), finish(status, patch), dismiss() }
```

三条踩过的坑：

- **`retention` 漏了会直接抛**：宿主在建条目时校验，报 `TypeError: 任务 completed 保留策略无效`；
- **收尾必须 `finish(status)`**，不能用 `update({status})` —— 只有 `finish` 才会排「自动收起」定时器，
  也才会在 `aborted` 时 abort 掉 `handle.signal`；
- **`start()` 只能从 `pending` 进 `running`**，所以同步要记 phase（本插件用 `taskId → { handle, phase }`），
  并把同步挂在状态变更的**唯一出口** `patch()` 上；移除任务 / 清空已完成 / 关开关 / 插件卸载都要 `dismiss()`，
  否则任务中心会留一堆幽灵行。

宿主没有 `ctx.tasks`（老版本）时静默降级：下载照常，只是不显示在任务中心。

## 六、排障

| 现象 | 原因 / 处理 |
| --- | --- |
| 「宿主本地接口服务未就绪」 | 主程序的 KuGouMusicApi 还没起来：确认版本 ≥ 2.3.2-beta.2，或重启主程序 |
| **「本次请求需要验证」** | 酷狗风控。插件会自动唤起宿主的**安全验证弹窗**，验完自动重试；如果被取消或没验过，任务行会标「需要安全验证」，点「重试」会再弹一次 |
| 「登录状态无效」 | 酷狗登录态过期，回宿主重新登录 |
| 只有 128K，想要更高 | 该歌的版权信息里就没有更高音质（非 VIP / 无版权）。任务行会标「请求 FLAC，已降级」 |
| 文件去了哪 | 系统默认下载目录（Windows 通常是 `%USERPROFILE%\Downloads`）。想指定位置用「另存为…」或「复制直链」 |
| 「可能只是试听片段」 | 实际体积远小于「码率 × 时长」，多半是没权限拿到完整版 |
| 一直停不下来 | 「停止」在分片之间生效，最多等当前分片（≤ 8 MB）下完 |
| 改了设置没反应 | 先比对进程启动时间与文件写入时间：进程比文件旧说明还跑着旧代码，重载插件列表或重启即可 |

排障时优先点「复制诊断」—— 里面带了设置、最近 12 个任务（含实际音质、分片与否、重试次数、错误）
与最近 8 条历史。

覆盖范围（都是**真的跑一遍业务流程**，不是静态检查）：

- 假 CDN 真实实现 Range 语义 → 断言拼装后的字节与源文件**逐字节一致**；
- 服务端忽略 Range（回 200 整包 / 分片中途回 200）自动降级；
- 音质降级顺序、128 用主 hash（夹具**故意乱序**）、只有 128K 时回退 `.mp3`；
- 业务错误（20018 / error_code=0 的连接错误）文案、图片字节误判、HTTP 500；
- 取消、批量勾选、云盘/无 hash 歌曲被拦截、历史持久化、另存为句柄写入、剪贴板失败兜底；
- **确认框**：内容渲染、音质/保存位置切换、选择位置（含取消）、确认后带对音质与句柄、
  「记住」写回设置、取消/Esc/Ctrl+Enter/点遮罩四条关闭路径、批量时「选择位置」禁用、云盘歌不弹框；
- **安全验证**：判定规则（成功响应里的 ssaCode 不算）、唤起验证→重试成功、
  取消后明确失败并标记 `needsVerify`、同一轮只弹一次、宿主没能力时的文案；
- **任务中心**：id 前缀与 retention 形态（漏了真机会抛）、pending→start→update→finish 的状态机推进、
  进度百分比递增、完成后换成「复制直链」、失败给「重试」并带错误文案、中止走 aborted、
  移除/清空/关开关时摘掉条目、老宿主没有 `ctx.tasks` 时静默降级；
- **复用宿主地址**：当前曲目 0 次上游请求、关掉开关后回退到接口、要更高音质时不偷懒、
  宿主地址失效自动回退 `/song/url`、上游风控失败时用曲目上残留地址救回、确认框里的提示；
- **借宿主解析通道**：auto 时请宿主解析（不打自己的接口）、宿主解析器抛异常/返回空时静默回退、
  显式音质时不动用宿主、自己请求被风控拦下后靠宿主救回、**用户主动取消验证时不再打扰**、
  关掉开关后改走自己的接口、老宿主没有解析器时降级；
- **歌词页按钮**：挂进 `.lyric-bar .bar-right`（不是整个底栏）、重复回调不重复挂、
  歌词页关闭时那一组被卸载、重新打开设置后主栏与歌词页都复位；
- **0 KB 空文件**：另存为与确认框两条路径在解析失败时都**不弹保存对话框**、
  下载失败时删掉已建出的空文件、成功路径不误删；
- **播放栏按钮**：宿主页面后出现才挂载、重复回调不去重、节点被抹掉后自动补挂、
  没歌在播置灰、开关能装能卸、点击拉起确认框；
- **CSS 契约**：设置根节点不得自带 `height:100%`/滚动，插件页必须自带（就是 1.0.0 的滚动 bug）；
- **响应式**：用 `watchEffect` 盯着渲染结果，确认队列变化与任务状态变化**真的驱动了界面**。

## 八、边界

- 只读写自己命名空间下的 `ctx.storage`；
- 网络请求只有两个去向：宿主内置的酷狗本地接口（`/song/url`）与歌曲 CDN 直链；
- 不加载任何第三方代码，不上传任何数据；
- **不绕过任何版权限制**：能不能下载、能下到哪个音质，完全取决于这首歌在你账号下的可播放权限 ——
  拿不到高音质就降级，拿不到就报错，插件不做任何尝试绕过。
